# Log Parser

A small Java 21 library and demo that parses application log lines, counts entries per level, and detects error patterns: repeated errors and error spikes.

## Log format

Each line must look like this:

```
YYYY-MM-DD HH:MM:SS LEVEL Message
2026-10-26 08:10:42 ERROR Failed to process payment: timeout
```

- `LEVEL` is one of `DEBUG`, `INFO`, `WARNING` or `ERROR`. Matching is exact and case-sensitive, so `WARN` and `info` are rejected.
- The message is optional.
- Dates are checked strictly: `2026-02-30` is rejected, not rolled over to March.
- Lines that don't match (stack traces, blank lines, unknown levels, impossible dates) are skipped, never thrown. Set `logparser` to `DEBUG` in `src/main/resources/logback.xml` to see why each one was skipped.

## Features

| Method | What it does |
| --- | --- |
| `parseLine(line)` | Parses one line into a `LogEntry`, or returns `Optional.empty()` if the line is malformed |
| `parseLines(lines)` | Parses many lines, keeping the valid ones in their original order |
| `countByLevel(entries)` | Counts entries per level; every level is included, zeros too |
| `findRepeatedErrors(entries)` | Lists `ERROR` messages that occur more than once, most frequent first |
| `topErrors(entries, n)` | Lists the `n` most frequent `ERROR` messages |
| `detectErrorSpikes(entries)` | Finds bursts of 3 or more errors within 5 minutes; an overload takes your own threshold and window |
| `buildAlertReport(entries)` | Returns a text report with the top 3 errors and every spike |

## Requirements

- JDK 21. Gradle downloads it automatically through a toolchain if it isn't installed.
- No separate Gradle install: the wrapper (`gradlew`, `gradlew.bat`) downloads Gradle 9.8.2 itself.

## Usage

On Windows use `.\gradlew.bat`; on macOS and Linux use `./gradlew`.

```sh
./gradlew build                     # compile, test and package
./gradlew test                      # run the TestNG tests
./gradlew run -q --console=plain    # analyze the bundled sample logs
./gradlew run -q --console=plain --args="path/to/app.log other.log"   # analyze your own files
./gradlew report                    # HTML dashboard, opened in your browser
```

### Visual report

`./gradlew report` parses the logs, writes `build/reports/log-report/index.html` and opens it in your default browser. For each log the page shows:

- summary tiles: lines read, parsed, skipped, errors, error rate, error spikes and time span
- a timeline of entries per time bucket, coloured by level, with error spikes shaded
- the breakdown by level, the most frequent errors and a table of the spikes
- the lines that were skipped, with line numbers, and every entry in a table you can expand

The page is a single file with no external dependencies, so it works offline and can be shared. It also follows your system's light or dark mode. Use the same `--args` as `run` to report on your own files, and add `--no-open` to write the file without opening a browser, for example `./gradlew report --args="app.log --no-open"`.

With no arguments, the demo analyzes the two sample logs in `src/main/resources/logs/`:

- `application.log` (1,510 lines, 08:00 to about 17:30): an ordinary business day. Errors are scattered, with one small burst after a 12:30 deploy that gets rolled back. It also contains realistic junk the parser skips: stack traces after errors, blank lines, impossible dates, unknown levels (`TRACE`, `WARN`, `info`) and a cut-off line.
- `incident.log` (1,383 lines, 09:00 to 12:00): warnings build up from 10:08, a database outage runs from 10:15 to 10:45, and a small aftershock follows at 11:33.

Both files are generated by `scripts/generate_sample_logs.py`, which uses a fixed random seed, so it produces the same files every time. To regenerate them, run `python scripts/generate_sample_logs.py src/main/resources/logs`.

Give it file paths and it analyzes those files instead. Relative paths are resolved against the project folder. Files are read as UTF-8, and a file that can't be read is reported as an error and skipped.

The build compiles with `-Xlint:all -Werror`, so any compiler warning fails it. The test report is written to `build/reports/tests/test/index.html`.

## Project layout

```
src/main/java/logparser/
  LogParser.java       parsing, statistics and error pattern detection
  LogEntry.java        one parsed line (an immutable record)
  LogLevel.java        the supported levels
  LogParserDemo.java   the demo: reads log files and logs the analysis
  LogSources.java      loads the bundled sample logs or files named on the command line
  HtmlReport.java      renders the HTML report (inline SVG charts)
  LogReportApp.java    the report command: writes the page and opens the browser
src/main/resources/
  logs/                sample logs: application.log, incident.log (generated)
  logback.xml          logging configuration
src/test/java/logparser/
  LogParserTest.java       TestNG tests for the parser
  LogSourcesTest.java      checks that the sample logs load and parse as documented
  HtmlReportTest.java      checks the report's content, escaping and number formatting
scripts/
  generate_sample_logs.py  regenerates the sample logs (Python 3, fixed seed)
```

## Logging

The code logs through the [SLF4J](https://www.slf4j.org/) API, and [Logback](https://logback.qos.ch/) writes the output at runtime. To use a different logging backend, replace the `logback-classic` dependency in `build.gradle.kts`; no code changes are needed.

# CLAUDE.md

Java 21 log parser for lines shaped `YYYY-MM-DD HH:MM:SS LEVEL Message`: parses them, counts entries per level, detects repeated errors and error spikes. Single-module Gradle project (Kotlin DSL), package `logparser`. Windows, git (branch `main`), no CI. `README.md` is the user-facing doc: update its feature table and demo output when they change.

## Commands

Run from the repo root. In Git Bash, use `./gradlew` instead of `.\gradlew.bat`.

```powershell
.\gradlew.bat build                  # compile + test + package; this is the full check
.\gradlew.bat compileJava            # compile only (stands in for a typecheck)
.\gradlew.bat test                   # all tests; report: build\reports\tests\test\index.html
.\gradlew.bat test --rerun           # force a rerun when Gradle reports test as UP-TO-DATE
.\gradlew.bat test --tests "logparser.LogParserTest"                                  # one class
.\gradlew.bat test --tests "logparser.LogParserTest.detectErrorSpikesReportsEachBurstOnce"  # one method
.\gradlew.bat run -q --console=plain # run the demo on the bundled logs (main: logparser.LogParserDemo)
.\gradlew.bat run -q --console=plain --args="C:\path\app.log other.log"  # analyze files on disk instead
.\gradlew.bat report -q --console=plain                     # HTML report -> build\reports\log-report\index.html, opens browser
.\gradlew.bat report -q --console=plain --args="--no-open"  # same, without the browser (use this when verifying)
```

- There is no linter, formatter or static-analysis plugin. The compiler is the lint step: `-Xlint:all -Werror` applies to main and test code, so any warning fails the build.
- Dependencies come from Maven Central on the first build; there is no separate install step. Versions are written inline in `build.gradle.kts`, not in a version catalog.

## Architecture & key paths

- `build.gradle.kts`: `application` plugin, Java 21 toolchain, `useTestNG()`, and the custom `report` task (`JavaExec` with main class `logparser.LogReportApp`).
- `src/main/java/logparser/`
  - `LogParser`: all domain logic (parsing, `countByLevel`, error pattern detection, `buildAlertReport`). It is stateless, so one instance can be reused.
  - `LogEntry`: record (`timestamp`, `level`, `message`); the constructor rejects nulls.
  - `LogLevel`: enum `DEBUG, INFO, WARNING, ERROR` plus `fromText`.
  - `LogSources`: input loading shared by both entry points. With no paths it reads the bundled logs from the classpath (`readResource`); otherwise it reads each path (`Files.readAllLines`, UTF-8). An unreadable file logs ERROR and is left out.
  - `LogParserDemo`: the `run` entry point. Each log goes through `analyze`, which logs the parsed count and level counts at INFO, each repeated error at INFO, and the alert report (top errors and spikes) at WARN. Spikes are not logged separately; the report already lists them.
  - `LogReportApp`: the `report` entry point. It removes `--no-open` from the arguments, writes `HtmlReport` output to `build/reports/log-report/index.html` (relative to the working directory) and opens it with `java.awt.Desktop`, falling back to logging the file URL. It exits with code 1 if no log could be read.
  - `HtmlReport`: builds the HTML page with `StringBuilder`; no template engine, no JavaScript, no CDN. Charts are inline SVG and the CSS is a text block at the bottom of the file.
- `src/main/resources/logs/`: the sample data, `application.log` and `incident.log` (about 1,400 lines each). This is input data, not code, and it is generated by `scripts/generate_sample_logs.py`.
- `src/main/resources/logback.xml`: the only logging config (`logparser` at INFO, root at WARN). It is also used by tests, because there is no `logback-test.xml`.
- `src/test/java/logparser/`
  - `LogParserTest`: the parser's behaviour.
  - `LogSourcesTest`: checks that the bundled logs load and still give the documented counts and spikes.
  - `HtmlReportTest`: checks the page content with `contains`, never the exact markup.

## Code conventions & patterns

- **Logging:** SLF4J only, never `System.out` or `System.err`. Each class declares `private static final Logger LOG = LoggerFactory.getLogger(X.class);`. Main code may import only `org.slf4j`, never `ch.qos.logback` (Logback is `runtimeOnly`).
- **Log levels:** `LogParser` logs only at DEBUG. Reporting at INFO or WARN belongs to callers such as `LogParserDemo`.
- **Bad input vs bad settings:**
  - Malformed log input never throws. `parseLine` returns `Optional.empty()`, `parseLines` drops the line, and both log the reason at DEBUG.
  - Invalid arguments (a negative limit, a threshold below 1, a null or negative window) throw `IllegalArgumentException`.
- **Return values:** public methods return unmodifiable collections (`toList()`, `List.copyOf`, `Collections.unmodifiable*`). Tests assert this.
- **Result types:** new result types go in `LogParser` as nested records, like `LogParser.ErrorCount` and `LogParser.ErrorSpike`, not as top-level files.
- **Timestamp parsing:** uses `DateTimeFormatter.ofPattern("uuuu-MM-dd HH:mm:ss")` with `ResolverStyle.STRICT`. STRICT requires `uuuu`; with `yyyy` every parse fails.
- **Timestamp formatting:** `LogParser.TIMESTAMP_FORMAT` (package-private) is the only full-timestamp format. Use it to parse and to print; never declare another `"uuuu-MM-dd HH:mm:ss"` formatter. Don't rely on `LocalDateTime.toString()`, which prints `2026-10-26T09:41` (with a `T`, and `:00` seconds dropped).
- **`ErrorSpike`** holds only its `errors` list, which is never empty. `start()`, `end()` and `count()` are computed from that list, so don't add fields for them.
- **HTML output (`HtmlReport`):**
  - Every log-derived string goes through `escape()` before it reaches the page, because log messages are untrusted.
  - Numbers in CSS, SVG or percentages go through `number()`/`percent()` (`Locale.ROOT`). A default-locale `String.format` would print `50,0` on comma-decimal machines and break the CSS.
  - Colours are CSS variables in `:root`, overridden in the `prefers-color-scheme: dark` block. Add new colours to both.
- **Section banners:** source files group members under `// ----` banner comments (Parsing, Statistics, Error pattern detection). Put new members under the matching banner.
- **Tests:**
  - Test methods are named `methodUnderTestExpectedBehaviour`.
  - Write input as raw log lines through the `parse(String... lines)` helper rather than building `LogEntry` objects.
  - Rejection cases go in the `malformedLines` `@DataProvider`.
  - TestNG's `assertEquals` takes `(actual, expected)`, the reverse of JUnit.

## Verification & guardrails

Before calling a task done:
1. `.\gradlew.bat build` passes with no warnings. Use `--rerun` if the tests show as up to date.
2. `.\gradlew.bat run -q --console=plain` still shows:
   - `application.log`: `Parsed 1432 of 1510 lines (78 skipped)`, `{DEBUG=381, INFO=816, WARNING=199, ERROR=36}`, spikes of 4 errors (12:32, the deploy) and 3 errors (14:32).
   - `incident.log`: `Parsed 1278 of 1383 lines (105 skipped)`, `{DEBUG=221, INFO=622, WARNING=226, ERROR=209}`, top error `Database connection refused` (130x), spikes of 29, 32, 38, 35, 33, 33 and 3 errors (10:15–10:45, then 11:33).
   If the sample logs change, update these values, `LogSourcesTest`, the incident assertions in `HtmlReportTest`, and the README demo output.
3. Add or update tests in `LogParserTest` for any change to `LogParser`'s behaviour.

Do not modify:
- `gradle/wrapper/*`, `gradlew` and `gradlew.bat`. These are generated; change the Gradle version with `gradle wrapper --gradle-version <v>`.
- `.idea/`. IntelliJ owns it and syncs from Gradle.
- Generated folders: `build/` and `.gradle/`. Never edit them or treat them as source.
- `.gitignore` already excludes `.gradle/`, `build/`, `out/`, `.idea/` and `*.iml`; never commit those.
- `.gitattributes` forces LF line endings in `gradlew`. Keep it: the global `core.autocrlf=true` would otherwise break the script on Linux.

## Gotchas

- **Sample logs are generated:** `scripts/generate_sample_logs.py` (Python 3, seeded per file name) produces both files. Never edit them by hand; change the script and regenerate with `python -I scripts/generate_sample_logs.py src/main/resources/logs`, then update every expected number listed under Verification.
  - The skipped lines are deliberate: stack-trace lines, `Caused by:` lines, blank lines, impossible dates, the levels `TRACE`/`WARN`/`info`/`FATAL`, and a cut-off line. Don't "fix" them; the expected counts depend on them.
  - The script asserts the file doesn't end with a blank line, because a reader drops a trailing blank line and the count would change.
  - Stack-trace lines start with 4 spaces; don't let an editor trim them.
- **No comments in sample logs:** `.log` files have no comment syntax. A `#` line would be counted as a skipped line and change the expected numbers, so explain sample data in docs instead.
- **Incident sample:** a dense outage from 10:15 to 10:45 comes out as 6 back-to-back spikes, because each spike covers at most 5 minutes and the search starts again after it.
- **Relative paths:** under `gradlew run`, relative paths in `--args` resolve against the project root. Paths that contain spaces need quotes inside the `--args` string.
- **Level names:** level matching is exact and case-sensitive (`WARN` and `info` are rejected). To add a level, add an enum constant. `countByLevel` returns an `EnumMap` with every constant, zeros included, so new levels show up automatically.
- **Error patterns:** they look only at `ERROR` entries and compare messages exactly, case included.
  - A spike is at least `DEFAULT_SPIKE_THRESHOLD` (3) errors with the last no more than `DEFAULT_SPIKE_WINDOW` (5 min, inclusive) after the first.
  - Errors are sorted by time first, and the search resumes after each spike, so a burst is reported once.
  - Ties in counts keep the order of first appearance (`LinkedHashMap` plus a stable sort). Don't swap in a `HashMap`.
- **Hidden debug logs:** DEBUG output is hidden by default, in tests too. To see why lines are skipped, set `<logger name="logparser" level="DEBUG"/>` in `logback.xml`, then set it back.
- **Timeline buckets:** the timeline picks the smallest bucket size from `BUCKET_MINUTES` that keeps it to 60 bars or fewer. Spike bands cover whole buckets so they line up with the bars; a band drawn by exact time would hide behind its bar when a spike fits inside one bucket.
- **Report screenshots:** to check the page visually, take a screenshot with headless Edge (`msedge --headless=new --screenshot=<png> --window-size=1200,3000 file:///...`).
  - Don't add a `#log-N` anchor to the URL; the screenshot comes out blank.
  - Headless windows can't be narrower than about 500px, so they can't show true phone width.
- **Demo output flags:** run the demo with `-q --console=plain`. Without them, Gradle's progress output gets mixed into the log lines.
- **Stale IntelliJ setting:** `.idea/misc.xml` still points compiler output at `out/`, a folder from the old `javac` setup. Ignore it; Gradle builds into `build/`.
